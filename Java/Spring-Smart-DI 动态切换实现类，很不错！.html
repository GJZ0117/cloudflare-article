Spring-Smart-DI 动态切换实现类，很不错！

作者：D哥

发布日期：2025年9月20日 11:25

来源：原文链接

凌晨一点多我们组在 debug，一个支付接口的实现逻辑，突然发现需要动态切换实现类。因为我们不同商户走的支付通道不一样，有的要支付宝，有的要微信，有的甚至是走境外的通道。结果发现以前写死在 Spring 配置里的实现类，根本没法动态换，这就尴尬了。后来我就想起之前玩过的一个小技巧 —— Spring-Smart-DI，用来做动态切换实现类，特别顺手。

为什么要动态切换实现类？

你想啊，正常我们在 Spring 里面写的 @Autowired，其实就是固定注入一个实现类，比如：

@Service
public class PayServiceImpl implements PayService {
    @Override
    public void pay() {
        System.out.println("默认支付逻辑");
    }
}

然后 Controller 里写：

@Autowired
private PayService payService;

这就死了，运行时没法说“今天用支付宝实现，明天用微信实现”。可业务一旦复杂，比如做 SaaS 平台，每个租户要求的实现类都不一样，这时候如果还用硬编码方式注入，那得疯。

Smart-DI 的思路

Smart-DI 其实就是利用 Spring 的 BeanFactory + 动态代理 + 上下文切换 来做的。说白了，就是给同一个接口注册多个实现类，然后在调用的时候，根据某个上下文（可能是线程变量、请求参数、配置中心）来动态决定用哪一个实现。

举个例子，我们有两个支付实现：

@Service("aliPayService")
publicclass AliPayService implements PayService {
    @Override
    public void pay() {
        System.out.println("调用支付宝支付逻辑...");
    }
}

@Service("wechatPayService")
publicclass WechatPayService implements PayService {
    @Override
    public void pay() {
        System.out.println("调用微信支付逻辑...");
    }
}

正常情况下只能注入一个，但我们用 Smart-DI 可以这么搞：

@Component
public class PayServiceRouter implements PayService {

    @Autowired
    private ApplicationContext applicationContext;

    @Override
    public void pay() {
        String channel = PayContext.getChannel(); // 从上下文获取支付渠道
        PayService target = (PayService) applicationContext.getBean(channel + "PayService");
        target.pay();
    }
}

这里的关键点就是 PayContext，它可以是 ThreadLocal 保存的，也可以是请求头解析出来的，总之就是把“我要用哪个实现”的信息传进去。这样就不需要在写死的时候选一个，而是运行时随时切。

Smart-DI 和普通多实现的区别

很多同学问，那我用 @Qualifier 注解不就行了吗？比如：

@Autowired
@Qualifier("aliPayService")
private PayService payService;

这只能在编译期定死，不能在运行时动态切换。而 Smart-DI 走的是“代理模式”，最终注入的只有一个 PayServiceRouter，里面帮你切换。这样就相当于给 Spring 加了一层“动态路由”。

更通用的写法

支付只是例子，其实所有有“策略模式”需求的地方都能用。比如不同租户要用不同的存储实现，一个走 MySQL，一个走 MongoDB，你只要写个 Router，就能在运行时自动选择。

稍微抽象一下：

@Component
public class SmartRouter<T> {

    private final ApplicationContext context;

    public SmartRouter(ApplicationContext context) {
        this.context = context;
    }

    public T route(Class<T> clazz, String beanName) {
        return context.getBean(beanName, clazz);
    }
}

然后使用时：

SmartRouter<PayService> router = new SmartRouter<>(applicationContext);
PayService payService = router.route(PayService.class, "aliPayService");
payService.pay();

这样完全解耦了，只要你在 Spring 容器里有这个实现类，想切就切。

和 AOP 结合

有意思的是，你还可以用 AOP 在方法执行前拦截，根据注解来决定用哪个实现。比如：

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface UsePay {
    String value();
}

然后写个切面：

@Aspect
@Component
public class PayAspect {

    @Autowired
    private ApplicationContext context;

    @Around("@annotation(usePay)")
    public Object switchImpl(ProceedingJoinPoint pjp, UsePay usePay) throws Throwable {
        PayService target = context.getBean(usePay.value(), PayService.class);
        return target.pay();
    }
}

这样 Controller 里就可以写：

@UsePay("wechatPayService")
public void doPay() {
    // 这里就会自动切到微信支付
}

是不是比手动路由更优雅？

实际坑点

当然，Smart-DI 虽然灵活，但也有坑。比如：

  1. Bean 名字容易写错，一旦错了直接 NoSuchBeanDefinitionException。
  2. 循环依赖更容易出现，因为你在运行时还要取 Bean。
  3. 调试难度大，别人一看 @Autowired PayService payService;，还以为就一个实现，结果运行时才发现是切换的。

所以我自己的习惯是，配合配置中心（比如 Nacos），统一管理“当前租户用哪个实现”，避免写死字符串。

我们系统有个报表导出功能，有的客户要 Excel，有的客户要 PDF，还有的要 CSV。一开始写了三个实现类，后来切换逻辑全写在 if-else 里，越来越臃肿。换成 Smart-DI 之后，就轻松多了，只需要在调用时告诉 SmartRouter：“这次要 excelExportService”，它自己就会去调用那个 Bean，代码再也不用堆满 if-else。

写到这，我脑子里又想起来昨天晚上被测试怼的那个问题：他们说为什么导出 Excel 失败，日志还打印了“调用 PDF 导出逻辑”？结果一看就是 PayContext（类似的上下文类）没设置好，默认走了另一个实现。可见上下文传递才是整个 Smart-DI 的关键，没搞好就全乱套。
