如果你最近在面字节、阿里、腾讯等头部大厂的大模型 Agent 岗位，你可能会发现一个残酷的现实：面试官很可能根本不会一上来就问你模型结构。

相比于背诵 Transformer 的原理，他们更喜欢直接抛出真实业务场景中的“地狱级”连环追问：

  • RAG 怎么降噪？


  • Agent 工具调用失败了怎么办？


  • KV Cache 到底解决什么问题？


  • Skill 太多导致命中率急剧下降怎么破？


今天这篇文章，我为你整理了大模型 Agent 岗位最高频的“夺命十连问”。看完这篇，看看在真实的工程场景中，你能答对几道？

Q1：RAG 检索出来的文档，要不要全部丢给大模型？


❌ 错误回答： 可以全丢进去，反正现在模型上下文窗口很大。

✅ 满分回答：绝对不能。

RAG 在实际落地中最大的坑，就是把检索结果无脑塞进上下文。记住：检索只是召回，不等于答案相关。在工程落地上，我们一般必须做以下几步：

  1. Top-K 召回：初步筛选最可能相关的片段。


  2. 重排（Re-rank）：利用专门的模型对召回结果进行二次相关性排序。


  3. 去重与过滤：剔除低相关、重复的冗余片段。


  4. 控制上下文预算：严格把控输入 Token 长度。


如果不做这些，文档越多，送入的噪声就越多，大模型反而越容易被带偏（即“大海捞针”中的注意力涣散）。

💡 一句话总结：RAG 不是把资料塞满，而是把最相关的证据精准送进去。

Q2：Agent 工具调用失败，该怎么处理？


❌ 错误回答： 捕获异常，给用户返回一句“工具调用失败，请重试”。

✅ 满分回答：必须分层处理。 Agent 调工具绝不是调用完就结束，要有完整的“错误恢复链路”。

  • 第一层：精准判断失败类型

    是参数缺失/错误？网络超时？权限不足？工具本身宕机？还是返回的 JSON 格式异常？


  • 第二层：执行自动修复（Self-Correction）

    根据错误类型，让大模型重写参数、执行重试、切换备用工具，或者对工具的中间结果进行校验。


  • 第三层：多次失败后的降级兜底

    如果穷尽尝试依然失败，需要明确告知用户当前的能力边界，给出可替代的建议方案，并在必要时转交人工或仅返回部分有效结果。


💡 面试加分项： 向面试官强调“Agent 的鲁棒性取决于它的容错和自愈能力”。


 Q3：预训练、SFT 和微调的核心区别是什么？


很多人会在这个问题上把概念绕晕。其实逻辑非常清晰：

  • 预训练（Pre-training）： 解决“会不会”的问题。让模型吃下海量无标注文本，目标是预测下一个 Token。这赋予了模型通用语言能力和基础世界知识。


  • SFT（监督微调）： 解决“听不听话、懂不懂格式”的问题。用高质量的“指令-回答”对，教会模型如何按照人类的意图去完成特定任务。


💡 面试加分项：
注意，SFT 本身就是微调（Fine-tuning）的一种。如果面试官问“预训练和微调的差别”，你可以按上面答；如果问“SFT 和微调的差别”，一定要补一句：“SFT 是微调流程中的一个具体阶段和方法。” 这个细节非常体现专业度。

 Q4：为什么不能把全部意图识别都交给大模型？


✅ 满分回答： 因为太贵、太慢，且毫无必要。

在真实的商业系统中，意图识别通常要走分层漏斗架构：

  1. 第一层（规则与关键词）： 处理极高频、完全确定性的意图。速度极快，成本为 0。


  2. 第二层（小模型分类器，如 BERT 类）： 处理常规的、稍显复杂的分类意图。


  3. 第三层（大语言模型）： 作为最终兜底，专门啃硬骨头，处理长尾、模糊、多意图交织的复杂场景。


这样做能最大化降低推理成本、压缩响应延迟、提升系统稳定性，并且极大地降低了线上治理的难度。

💡 一句话总结：好钢用在刀刃上，大模型应该用来解难题，而不是做所有题。

Q5：RAG 里的 Top-K，是不是越大越好？


❌ 错误回答： 是的，K 越大找到正确答案的概率越高。

✅ 满分回答：不是，这里存在一个“召回率 vs 噪声”的 Trade-off。

  • K 太小：容易漏掉关键证据（Recall 不足）。


  • K 太大：会引入大量无关内容，造成上下文污染，不仅拖慢推理速度，还会增加幻觉风险。


在工程实践中，K 的取值需要综合考量：文档切片（Chunk）大小、向量模型的能力、重排（Re-rank）模型的效果、上下文窗口预算以及业务的容错度。

💡 高级解法：

 抛弃固定的 K 值（如死板的 K=10），采用 动态 Top-K + Re-rank + 相似度阈值截断，才是当前更成熟的做法。

Q6：KV Cache 到底解决的是什么问题？


✅ 满分回答： 解决的是大模型推理阶段的重复计算问题。

大模型在自回归生成时，是一个 Token 接着一个 Token 往外吐的。如果每生成一个新 Token，都要把前面所有历史 Token 的 Key 和 Value 矩阵重新计算一遍，算力成本将是灾难性的。

KV Cache 的原理就是把历史 Token 的 Key 和 Value 提前缓存下来在显存里。下一步生成时，只需计算当前新 Token 的状态，并直接复用历史缓存，从而实现：

  • 显著加速解码（Decoding）过程


  • 大幅降低延迟


  • 提高系统的整体吞吐量（Throughput）


💡 一句话总结：KV Cache 没法提升模型的“智商”，但能极大地提升它的推理“手速”。

Q7：Embedding 向量效果差，可能是什么原因？


❌ 错误回答： “可能是因为用的向量模型太小或者不够好。”

✅ 满分回答： （展现工程思维，从整个 Pipeline 找原因）

  1. 切片（Chunking）不合理： 切得太碎导致上下文语义断裂；切得太大又包含过多噪声。


  2. 模型领域不匹配： 比如中文业务用了英文偏向的模型，或者垂直行业（如医疗、法律）直接用了通用模型，导致专业术语无法映射。


  3. Query 与 Document 表达不对称： 用户提问是随意的口语，而知识库是严谨的术语，两者在向量空间里的距离天生很远。


  4. 缺少元数据（Metadata）过滤： 没有将时间、权限、文档类型等结构化标签引入检索逻辑，纯靠向量“盲搜”。


  5. 缺乏评测基准： 如果没有建立起标准的 Query-Doc 黄金测试集，你连“到底哪里差、差多少”都无法量化。


Q8：Agent 的 Skill（工具）太多，导致命中率下降怎么办？


当 Skill 数量爆炸时，这就变成了一个经典的“工具路由（Tool Routing）”问题。解决方案有四个切入点：

  1. 优化 Skill 描述（Prompting）： 必须用大模型易懂的语言，清晰界定工具的适用场景、输入输出规范、边界条件，甚至提供正反例（Few-shot）。


  2. 分层路由架构： 坚决避免让模型在 100 个工具里直接做单选题。先预测“一级类目”，再下钻到具体工具。


  3. 引入召回与精排机制： 把选工具当成搜索来做。先用 Embedding 或关键词召回候选 Top-N 工具，再交由大模型做精排挑选。


  4. 负样本微调： 如果有自研模型，不仅要教它什么时候“该用”，更要注入负样本教它什么时候“不该用”。


💡 一句话总结：工具多本身不可怕，可怕的是系统里没有建立起高效的路由体系。

 Q9：RLHF 和 SFT，谁在前谁在后？


✅ 满分回答： 通常是 先 SFT，再 RLHF。

标准的对齐（Alignment）训练管线如下：

  1. 预训练（PT）： 获得基座模型。


  2. SFT（指令微调）： 用高质量数据教模型学会对话格式和遵循人类指令。


  3. RM（奖励模型训练）： 训练一个能给模型回答打分的“裁判”。


  4. RLHF（强化学习）： 使用 PPO 等算法，根据裁判的打分不断优化模型，对齐人类价值观偏好。


💡 面试绝杀：
别忘了补充一句：“现在实际落地中，为了降低工程复杂度，很多团队会跳过复杂的传统 RLHF（PPO），直接采用 DPO（直接偏好优化）等更轻量、稳定的方法。” 这句话一出，立刻证明你紧跟前沿实战。

Q10：RAG 出现幻觉（Hallucination），怎么缓解？


RAG 的幻觉主要分两类，需要对症下药：

  • 类型一：没搜到正确证据，模型开始“脑补”。


  • 类型二：搜到了对的证据，但模型理解错了或过度发散。


组合拳缓解方案：

  • 强基建： 优化检索质量与重排策略，确保正确的信息能排在最前。


  • 强约束： 在 Prompt 中严厉限制：“必须且只能基于参考文档回答。如果文档未提及，必须回答‘不知道’。”


  • 加质检： 生成前做证据相关性检查（NLI）；生成后做一致性校验，或者要求输出必须包含对原文的精确引用（Citation）。


💡 核心认知：
Prompt 约束永远只是最后一道防线。真正能根治 RAG 幻觉的，是

高质量的检索 + 强关联的溯源机制。
